# KerOp spectrum artifact (v1)

KerOp exports a **forward** spectrum. SpecInv consumes that spectrum and learns
a **spectral filter**. This file is the contract for the file they pass, not a
new theorem and not a claim about either paper.

Schema id: `kerop.specinv.spectrum/v1`

## What the file is

A versioned `.npz` (arrays) plus a sibling `.json` (same header, eigenvalues
inline). Either suffix is accepted by `specinv.spectrum_contract.load_spectrum_artifact`.

| Field | Type | Meaning |
|---|---|---|
| `schema` | string | Must be `kerop.specinv.spectrum/v1` |
| `schema_version` | int | `1` |
| `operator_id` | string | Stable id of the KerOp instance, e.g. `kerop.spectral/v1:r=0.5:b=0.6666666667:n=2048:dv=6:seed=20260301` |
| `seed` | int | KerOp `SpectralOperatorModel` seed |
| `n` | int | Number of exported 1-D modes (length of `eigenvalues`) |
| `feature_count` | int | Random-feature count `M` attached to this export (Theorem 3.4 prescription at a reference `n`) |
| `eigenvalues` | float[n] | Positive, **non-increasing** 1-D forward spectrum. SpecInv uses these as singular values \(\sigma_n\). For the joint instance they are KerOp's input-mode weights \(\mu_j = j^{-1/b}\). |
| `rf_spectrum` | float[] (optional) | Flattened KerOp product-set \(\{\mu_j\nu_k\}\), sorted descending. The KerOp bar is run on this instance, not on a different operator. |
| `r`, `b` | float | Source / capacity exponents of the KerOp model |
| `output_dim` | int | KerOp \(d_v\) |
| `ill_posedness` | float | \(p = 1/b\), stored so SpecInv does not have to refit it |
| `source` | string | `kerop.SpectralOperatorModel` |
| `kerop_version` | string | KerOp package version that wrote the file |
| `fingerprint` | string | First 16 hex chars of SHA-256(`schema`, `operator_id`, `seed`, `eigenvalues`) |

The committed fixture `fixtures/kerop_spectrum_v1.npz` was generated by

```bash
python -m specinv.spectrum_contract --write fixtures/kerop_spectrum_v1.npz
```

which **imports KerOp** and calls `SpectralOperatorModel`. It is not a
hand-written copy of SpecInv's old `power_law_operator` table.

## Joint instance (the one path)

Defaults in `specinv.spectrum_contract`:

* \(r = 1/2\), \(b = 2/3\), \(n = 2048\), \(d_v = 6\), seed `20260301`
* Then \(\mu_j = j^{-3/2}\), so SpecInv's inverse problem is the §5.1 spectrum
  (\(p = 3/2\)) **because KerOp emitted those weights**, not because the joint
  script called `power_law_operator` as a fallback.
* KerOp's matched-excess-risk bar is invoked on **this** `SpectralOperatorModel`
  (same `r, b, seed, d_v`), not on a silent substitute.

## How SpecInv finds the file

`specinv-joint` resolves, in order:

1. `--spectrum PATH`
2. a sibling KerOp checkout / `--kerop-root` / `KEROP_ROOT` — **export a fresh
   artifact** via the contract
3. the committed fixture above, still only after KerOp has been imported

If KerOp cannot be imported, the joint script **exits non-zero**. It does not
rerun the old 1-D suite and call that a joint result.

## What this is not

* Not a new rate theorem.
* Not a 100x (or any other invented-factor) claim.
* Not GPU RF, imaging, FEM, NeuroFEM, a localizer, or Loihi.
